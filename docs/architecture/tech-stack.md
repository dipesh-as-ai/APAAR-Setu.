# APAAR Setu Technology Stack

## 1. Stack Decision

The prototype uses a modular monolith with a separate worker process. This is the smallest architecture that supports reliable validation, review workflows, background processing, API integration, and a credible future scale path.

```text
React Web App
       |
API Gateway / Reverse Proxy
       |
FastAPI Application
       |
PostgreSQL + Redis + Object Storage
       |
Validation Worker and External Adapters
```

## 2. Frontend

- Framework: React 19 with TypeScript.
- Build tool: Vite.
- Routing: TanStack Router or React Router. Use one, not both.
- Server state: TanStack Query.
- Forms and validation: React Hook Form with Zod schemas.
- Styling: Tailwind CSS with project-owned design tokens.
- Accessible components: Radix UI primitives or owned semantic components.
- Icons: Phosphor Icons, one icon family only.
- Charts: Apache ECharts.
- QR display: a maintained QR component.
- Testing: Vitest, Testing Library, and Playwright.
- Error reporting: structured client error boundary with correlation ID display.

The frontend consumes generated API types. It must not duplicate server-side authorization or validation rules as its only enforcement layer.

## 3. Backend

- Language: Python 3.12 or later within the supported deployment image.
- Framework: FastAPI.
- Validation: Pydantic v2.
- ORM and migrations: SQLAlchemy 2.x and Alembic.
- Database driver: psycopg.
- Authentication integration: OIDC with Keycloak in a realistic environment; a local JWT provider may be used for the first demo.
- Background jobs: Celery with Redis, or a small worker abstraction that can later use Celery.
- CSV parsing: Python csv module for controlled CSV input; Pandas only where justified.
- Excel parsing: openpyxl with formulas and macros disabled.
- Fuzzy matching: RapidFuzz for review candidates only.
- Signing: `cryptography` with Ed25519.
- QR generation: QRCode library containing only an opaque verification URL.
- API schema: OpenAPI generated by FastAPI.
- Logging: JSON logs with correlation ID and redaction middleware.

## 4. Data and Infrastructure

- Transactional database: PostgreSQL 16 or later.
- Cache and job broker: Redis 7 or later.
- Upload storage: local object-storage-compatible service for prototype, such as MinIO, or a mounted development directory with a storage abstraction.
- Reverse proxy: Caddy or Nginx for local HTTPS and route protection.
- Local orchestration: Docker Compose.
- Production orchestration path: managed containers or Kubernetes after the domain model is stable.
- Observability: OpenTelemetry-compatible traces and metrics; structured logs in the prototype.

## 5. Development Tooling

- Package manager: pnpm for frontend workspace dependencies.
- Python environment: `uv` or Poetry. Use one consistently.
- Formatting: Prettier for TypeScript and Ruff format for Python.
- Linting: ESLint and Ruff.
- Type checking: TypeScript strict mode and mypy or pyright for typed backend modules.
- Git hooks: lint and focused tests before commit when a repository is available.
- Environment configuration: `.env.example` and typed settings; never commit real secrets.

## 6. External Adapter Boundaries

The application uses interfaces instead of direct calls from domain code:

- `ApprovalAdapter`
- `IdentityAdapter`
- `NotificationAdapter`
- `CredentialAdapter`
- `InstitutionIntegrationAdapter`

Each adapter has a fake implementation for tests and prototype demos. The real implementation is not required until the external service contract, authentication, rate limits, and data-sharing authority are available.

## 7. Deployment Profiles

### Demo profile

- One web container.
- One API container.
- One worker container.
- PostgreSQL.
- Redis.
- Local object storage.
- Seed command.

### Pilot profile

- Managed PostgreSQL with backups.
- Managed object storage.
- Managed Redis or queue.
- OIDC provider.
- HTTPS and WAF.
- Centralized logs and metrics.
- Separate staging and production environments.

### Production evolution

- Horizontal API and worker scaling.
- Read replicas or analytics projection.
- Managed key storage or HSM for signing keys.
- Disaster recovery and retention policies.
- VAPT, operational monitoring, and incident response.

## 8. Deliberately Deferred Technologies

- Kafka is deferred until upload volume and event replay requirements justify it.
- ClickHouse is deferred until dashboard query volume requires it.
- Kubernetes is deferred until a multi-service deployment needs orchestration.
- Machine learning is deferred until labelled historical data exists.
- Blockchain is not required; signed records and an append-only audit trail provide the needed prototype properties.

## 9. Local Runtime Requirements

- Docker Desktop with Compose.
- Node.js LTS and pnpm for frontend development outside containers.
- Python 3.12 and the chosen environment manager for backend development outside containers.
- PostgreSQL and Redis are supplied through Compose.
- A modern browser.
- At least 4 GB available memory for the full local stack.

## 10. Environment Fallback

The target data store is PostgreSQL. When Docker or a local PostgreSQL service is unavailable, the prototype uses SQLite through the same repository boundary so development and UI execution can continue. Production deployment must use PostgreSQL and run the database migration suite against PostgreSQL before release.
